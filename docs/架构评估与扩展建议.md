# EdaKit 架构评估与扩展建议

> 此文是改造前评估。2026-10-21 已完成当前应用的相应整理与加固，现状以[架构加固实施与验证](架构加固实施与验证.md)为准；新业务扩展边界仍保留作参考。


评估日期：2026-10-21。范围：当前源码、通信与部署边界、已有测试。此次仅审查，不修改运行代码。

## 结论

当前架构支持继续扩展，建议保持模块化单体：CEF 作为展示层，Python 负责数据与转换，Capture Tcl 负责宿主操作。无需重写，也不需要引入微服务或通用插件引擎。

它目前是按功能目录组织的应用，还不是可插拔平台。增加筛选、详情字段、预览工具等可以渐进实现；增加多个数据源、多 Capture 会话定向操作、批量任务或新宿主之前，应先收敛应用服务和通信协议。

用户已反馈最新功能与退出测试正常。此前记录的自动回归为 317 passed / 1 skipped，冻结程序 11 项自检通过。本轮未重新执行测试，也未独立复现 Capture 退出；用户反馈与已有自动验证分开记录。

## 已有结构与可复用部分

| 层次 | 当前实现 | 扩展基础 |
| --- | --- | --- |
| 展示 | server/web 中的 HTML、CSS、JS，CEF 承载 | 兼容现有 Capture CEF；可以继续模块化，框架不是必要条件 |
| HTTP 与编排 | server/app.py、cli.py、pipeline.py | 已有 API、命令行和产物准备入口，但编排边界需要统一 |
| 数据源 | catalog、fetch、easyeda/parse.py | 商城取数和 CAD 解析已分离，尚无统一数据源契约 |
| 中间模型 | easyeda/model.py 的 Component、Symbol、Footprint、Model3D 等 | 几何模型已有复用价值；未来可逐步迁到源无关的 domain 包 |
| 输出与预览 | symbol、footprint、render、threed | 转换器与渲染器已有独立模块，是当前较好的扩展点 |
| 宿主适配 | bridge/queue.py、install/templates/edakit.tcl | 文件协议兼容老 Tcl；目前是专用放置通道 |
| 生命周期 | server/lifecycle.py | 进程跟踪、启动互斥、退出清理已单独封装 |

## 需要优先处理的边界

### 1. 统一业务编排，优先级 P1

server/app.py 的 MallHandler 同时承担路由、商城查询、缓存、解析、渲染、配置和放置准备。_do_place 直接创建 PlaceRequest，且以 embedded 参数决定 capture_only；业务产物范围与入口形式发生耦合。

cli.py 的 cmd_build 另有取数、解析、生成符号 XML、封装、3D 映射的编排，与 pipeline.stage_component 部分重叠。虽然命名函数等已经共享，后续增加校验或导出策略仍需要检查多个入口。

建议先提取 CatalogService、ComponentService、PlacementService、ExportService。HTTP 与 CLI 只负责输入输出；以明确的准备选项表达 Capture 放置或完整导出。保留不同入口需要的不同输出目录和产物，不强行合并成同一行为。

### 2. 放置协议需要为任务与会话扩展，优先级 P1

bridge/queue.py 的 PlaceRequest 是固定放置字段，没有协议版本、命令类型和目标 Capture 会话。Tcl processQueue 扫描同一目录，读取后处理，再删除请求，没有处理前的原子领取步骤。

因此，生命周期支持多个 Capture 进程，不等于请求可以准确发给某一个 Capture。多个进程同时轮询时存在竞争或重复处理的可能。这是代码层面的风险，不是本轮已观察到的用户故障。

另一个具体边界是 submit 直接写最终 .req 文件，消费者可能在写入完成前读取。建议先写临时文件，再原子改名发布；消费者原子领取。响应也采用完整写入后发布，避免读到半份状态。

后续按需求增加 protocol_version、command、request_id、target_session、过期时间与稳定错误码；区分排队、准备中、等待原理图、启动放置、失败等状态。不要将启动交互式放置等同于用户已点击完成元件落点。

### 3. 前端状态需要拆分，优先级 P2

embed.js 在一个闭包内用单个 state 管理筛选、列表、详情、放置、预览旋转、布局与等待提示。当前规模可维护，但新工具页会增加跨功能状态影响。CSS 也应随模块拆分整理，避免继续叠加覆盖规则。

建议拆为 api、catalog、selection、preview、placement、layout 模块，共享少量明确状态和事件。可以使用构建时打包，输出仍须符合真实 CEF 的语法与功能能力。不要直接依赖现代浏览器特性或将 WebGL 当作默认能力；保持 PNG/Canvas 预览路径。

### 4. 缓存和后台任务缺少统一所有者，优先级 P2

server/app.py 使用模块全局缓存，组件和商品信息还共用一个字典、用键前缀区分。现有 render/scheduling.py 已经提供重复请求合并和单渲染槽，这是有价值的性能基础。

但预览渲染的并发限制不覆盖所有 HTTP、下载和业务任务；客户端中止请求也不等于后端取消。后续批量导入或密集预览需要任务协调器，定义并发上限、最新预览优先、过时任务丢弃和退出策略。缓存按组件、商品、分类、渲染分别管理容量、TTL、线程同步和统计。不能简单通过增加线程提升性能。

### 5. 配置、错误与数据源契约需逐步稳定，优先级 P2

Config 当前在 bridge/queue.py 内，已承担库目录、宿主、预览校准、网络端口等应用配置；没有显式版本迁移链。建议迁到配置模块，增加版本、类型验证和原子保存，继续保留已有绝对库路径。

MallClient、Fetcher 和 StepFetcher 由调用方直接创建。接入第二个数据源前，再提取 CatalogProvider、ComponentProvider 和 ModelProvider 契约，统一来源加器件编号的标识，避免假定所有器件都是 LCSC CID。当前不必为未确定的数据源提前造注册平台。

错误传播仍有字符串消息，日志分布于 Tcl 与后台输出。建议以 request_id 串联 HTTP、生成、队列、Tcl 和返回结果，增加稳定错误码及各阶段耗时。测试中已有较多直接 monkeypatch 具体类的方法，服务提取后可改为注入替身，减少测试与内部实现绑定。

## 后续功能的实施判断

| 计划功能 | 当前支持程度 | 建议前置工作 |
| --- | --- | --- |
| 新筛选项、详情字段、预览工具 | 可渐进增加 | 小步拆前端模块与服务方法 |
| 收藏、历史记录 | 可增加，当前未见独立存储边界 | 建立版本化持久化模块 |
| 完整导出与批量处理 | 部分基础已有 | 统一导出编排、建立有界任务与取消规则 |
| 第二数据源 | 需适配改造 | 数据源接口与来源标识，复用中间模型 |
| 多 Capture 定向放置 | 当前协议不足 | 会话绑定、原子领取、去重与版本化协议 |
| 新宿主或 Allegro 深度集成 | 转换代码可部分复用 | 独立宿主适配与真机验证；现有导出不代表已完成原生集成 |

## 推荐实施顺序与验收

1. 先提取应用服务，保持当前 API 和队列兼容；验证 HTTP、CLI 生成的器件名与目标产物一致，保留各自导出语义。
2. 再加固队列发布、领取和会话协议；验证并发提交、两个消费者、进程中断及旧请求兼容。
3. 拆分前端并统一缓存与任务管理；对比同一机器、相同冷暖缓存下的查询、首次预览、旋转及准备耗时，并检查线程数和内存是否趋于稳定。
4. 实际出现第二数据源、新宿主或独立工具页时，再添加相应契约和导航边界。

每一步都保留可部署的 CEF 基线、旧配置路径与 ASCII Tcl，并执行相关自动回归和 Capture 真机验证。无需一次性完成所有目录调整。
