## 原问题与修复

原服务在启动后无限休眠，只有手工Ctrl+C才走shutdown，未监控Capture生命周期。因此无控制台后台模式下，Capture退出后确实可能留下服务。原heartbeat只用于在线状态判断，不负责关闭进程。

新Tcl启动服务时传 `serve --capture-pid <Capture PID>`，并在运行目录capture_hosts中注册每个加载插件的Capture进程。服务打开Windows进程句柄，查询真实退出状态；不依赖父PID的瞬时查询，也不因Tcl心跳变旧而关闭服务。记录文件时间与进程创建时间交叉核对，拒绝陈旧PID记录误认新进程。

多个Capture进程共用服务时，任何一个已注册进程仍存活就继续运行；最后一个结束后，经短暂空会话宽限再关闭HTTP监听、释放进程句柄并退出。处理HTTP请求的线程是daemon，半截请求不阻止退出。只删除属于本服务的url.txt，保留另一服务新写的地址；不清空用户队列、配置、器件库或日志。

同一运行目录使用Windows命名互斥对象抑制重复启动；异常退出时由系统释放。PyInstaller单文件版正常有启动器和Python工作进程两个edakit.exe，两个都退出才算清理完成。

手工从命令行运行 `edakit-cli.exe serve` 未传capture-pid时，属于独立调试服务，按设计保持运行直到Ctrl+C，不自动绑定Capture。日常使用菜单由Tcl带上归属参数；不应将独立调试服务当作生命周期验收对象。

## 实测与边界

没有关闭用户Capture或工程。使用真实Windows进程模拟宿主，并实际运行打包后的无控制台exe：

| 场景 | 结果 |
|---|---|
| 两个宿主，先正常退出一个 | 服务继续运行 |
| 心跳时间写为过期值，但宿主仍在 | 服务保持，未误关 |
| 重复启动第二份服务 | 第二份自动退出，原地址保持 |
| 最后宿主强制结束，HTTP处理线程还等半截请求 | 约5.54秒后服务退出，启动器和工作进程均已结束 |
| 最后宿主正常结束 | 约6.03秒后两进程退出 |
| 退出前url.txt被另一服务更新 | 新地址被保留 |
| 已死亡宿主、PID重用及句柄释放 | 单元用例通过，旧记录不会保持服务存活 |

样本退出时间包含监控轮询、宽限、HTTP关闭和冻结启动器清理，不是所有机器的硬上限。真实Capture及其插件退出仍需下面的真机步骤确认，不能将模拟测试写成已实际关闭Capture验证。

6. 若常用多Capture实例，重新打开两个实例并进入商城；先关其中一个，服务应保留；关最后一个后，再等待10秒，应无主路径后台进程。不要求强制结束实际Capture来做异常测试。

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'edakit.exe'" |
  Where-Object { $_.ExecutablePath -eq 'E:\outputs\edakit\dist\edakit.exe' } |
  Select-Object ProcessId, ParentProcessId, CommandLine

Get-Content "$env:LOCALAPPDATA\edakit\background.log" -Tail 40
```

若仍残留，反馈上述完整进程输出、关闭后等待时长和background.log最后80行；不要先结束这些进程，以便区分旧服务、手动独立服务和新受管服务。后续是否清理按具体PID和路径处理。
