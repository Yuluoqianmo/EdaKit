### A2. 校准中修正的问题（都在代码注释里标了出处）

1. **符号坐标**必须 `(ee - BBox中心) * 0.254` 且 **Y 翻转** —— 原先只翻转没减中心。
2. **封装坐标**必须 `(ee - 画布原点) * 0.254`，**Y 不翻转** —— 原先没减原点。
3. **`TRACK` 字段序**是 `stroke_width(1) layer(2) net(3) points(4)` —— 原先搞反了宽度和层。
4. **`PAD` 字段序**：`number=[8], hole_radius=[9], points=[10], rotation=[11]` —— 原先把 hole 当成 rotation。
5. **`TEXT` 字段序**：`x=[2], y=[3], rotation=[4], text=[12]` —— 原先整体错位。
6. **层号映射**：`3=TOP_SILK`（原写成内层）、`11=MULTI_LAYER`、`7/8=阻焊`。
7. **`hole_radius` 是半径**，Capture/Allegro 的 drill 要直径，须 ×2。
8. 封装名应取 `c_para.package`（如 `LQFN-56_L7.0-W7.0-P0.4-EP`）。

### B1. 构建脚本踩过的坑（已修）

**坑 ①：`build_exe.bat` 是 LF 行尾 + 无 BOM 的 UTF-8。**
用户双击后只看到「按任意键继续」就结束，目录里连 `.venv` / `dist` 都没生成 —— 脚本在建虚拟
环境之前就退出了。`cmd.exe` 按 CRLF 断行，LF-only 的批处理在带括号的 `if (...)` 块上会解析错乱；
编码又是 UTF-8 而中文控制台默认 936(GBK)，报错全成乱码，等于没有提示。

**坑 ②：PowerShell 5.1 会把传给原生 exe 参数里的双引号吃掉。**
改用 `build_exe.bat`(ASCII+CRLF) + `build_exe.ps1`(UTF-8 BOM+CRLF) 之后仍然失败，日志里是：

```
python.exe :   File "<string>", line 1
    import sys;print(sys.executable);print(%d.%d%sys.version_info[:2])
                                           ^
SyntaxError: invalid syntax
```

探测脚本原本写的是 `'...print("%d.%d"%sys.version_info[:2])'`，但那对双引号在 PowerShell 5.1
往原生 exe 传参时被剥掉了，Python 收到的是残缺代码。**用户机器上 Python 3.13 是装好的
（`%LOCALAPPDATA%\Programs\Python\Python313\python.exe`），是探测本身把自己搞崩了。**

修法：探测只用**不带任何引号**的 `--version`，并用解析出的完整路径调用（不靠 PATH 查名）；
另外加上「扫常见安装目录 → py 启动器 → PATH」三级候选、跳过 Microsoft Store 的占位程序、
把跳过原因打印出来。脚本最后还核对产物是否存在并报大小，明确打印「构建成功 / 构建失败」。

**教训**：给原生程序传参时，参数里不要有引号 —— 这在 PowerShell 5.1 上不可靠。

**坑 ③：打包入口写成了包的 `__main__.py`。**
构建终于成功、exe 也生成了（7.1 MB），但用户双击后立刻报：

```
File "__main__.py", line 3, in <module>
    from .cli import main
ImportError: attempted relative import with no known parent package
```

spec 原来写的是 `Analysis(["src/lcsc2cadence/__main__.py"], ...)`。PyInstaller 会把这个文件
当作**独立的顶层脚本** `__main__` 编译，**包上下文丢失**，那行相对导入必然失败。

注意这里有个容易骗过自己的地方：`python -m lcsc2cadence` 是**能跑**的（那种调用方式下
它有父包），所以「-m 能跑」完全不能证明「打包能跑」。两者走的是不同的路径。

修法：新增根目录 `entry.py`，内容是绝对导入 `from lcsc2cadence.cli import main`，
spec 改为 `["entry.py"]`（保留 `pathex=["src"]`）；包内的 `__main__.py` 保留给
`python -m lcsc2cadence` 用。

**教训（最重要的那条）**：「打包成功」≠「exe 能用」。所以加了第三道防线 ——

### B3. 第三次构建：PyInstaller 卡死，以及把构建挪出 AppData

修好入口后用户再次构建，这次 exe 没出来 —— 卡在 PyInstaller 的
`Analyzing modules for base_library.zip ...` 一行上不动了。诊断凭据：

| 观察 | 数据 |
|---|---|
| `build_log.txt` 最后修改 | 09:21:54，此后 10 分钟无写入 |
| `build/` 目录文件数 | **0**（PyInstaller 连工作目录都没写） |
| `dist/` 里的 exe | 还是上一版（17:31） |

也就是卡在 analysis 里**只读不写**的那一段。对照实验：**同一份 spec、同一份源码，
在 Linux 沙盒里打包只要 9.9 秒**（PyInstaller 不是罪魁）。

推断是环境问题：工程目录在 `AppData\Local\Claude-3p\...` 这种深处 ——
杀毒软件会实时扫描，桌面应用的文件监视器也在盯着这个目录，而 analysis 阶段
要对几万个文件做 stat/open。

**改法**：脚本先把源码（不含 `.venv`/`build`/`dist`）镜像到
`%USERPROFILE%\lcsc2cadence-build`，在那儿建 venv、构建，最后把 exe 拷回工程的 `dist\`。
镜像失败会自动退回原目录（只警告，不中断）。

### B4. 顺手做的两件事：心跳 + 卡死看门狗

卡死最难受的地方是「安静」和「慢」长得一模一样。所以：

- 打包阶段每 10 秒打印一次 `已用时间 / 静默时长 / PyInstaller 最近一行日志`；
- **连续 10 分钟零输出 → 判定卡死，自动杀掉子进程并报构建失败**（不再无限等）；
- 子进程带 `PYTHONUNBUFFERED=1`（否则 Python 的输出会攒够 8 KB 才吐出来，心跳就废了）；
- PyInstaller 的完整输出另存 `pyinstaller_log.txt`/`pyinstaller_err.txt` 并拷回工程目录。

> 踩到的一个细节：**PyInstaller 的日志走 stderr，stdout 基本是空的**。第一版心跳只 tail
> stdout，结果一直显示空白 —— 等于没做。现在两个文件都算上。

### B8. 探测脚本自身修掉的两个 Tcl bug

B1 要靠 `probe.tcl` 给出结论，所以它自己先得是对的。用 `tclsh` 实跑时抓到两个：

1. **双引号里的 `[...]` 是命令替换**。写 `puts "  [可以] ..."` 时 Tcl 会去执行名为
   `可以` 的命令 → `invalid command name "可以"`，而外层 `catch` 把它吞了，
   于是输出停在「结论」两个字。改成花括号字符串 `puts {  [可以] ...}`。
2. **`set seen {}` 之后不能再 `set seen($k)`** —— base 是标量时报
   `can't set "seen(.)": variable isn't array`。改成 `unset -nocomplain seen; array set seen {}`。

另外把探测脚本做厚了：

- 找不到 `XMATIC_XML2OLB` 时，会去 `CDSROOT` 附近的常见目录里找 `*DboTcl*` / `*xmatic*` /
  `*captcl*.dll` 并尝试 `load`，然后**再查一次** —— 有些安装里扩展默认没加载，
  直接报 MISSING 会误判。
- 打印 `info loaded`（已加载的扩展），Failure 时我能据此判断该 load 哪个 DLL。
- 结论分成三档：`[可以]` / `[部分]`（只能写不能读回）/ `[不行]`。

插件侧也加了 `ensureXmatic`：真正放置前先试一次加载，菜单「能力探测」也会先试，
避免用户明明能用却被报 MISSING。

`tests/test_tcl_plugin.py` 新增 3 个用例把这两个坑钉住（无 XMATIC 时结论必须打印出来、
有 XMATIC 时结论是 `[可以]`、去重逻辑不得报 array 错误）。

### B9. 真机反馈：Capture 17.2 报 `missing close-brace` —— TCL 模板必须纯 ASCII

用户在 Capture 17.2（`D:/Cadence/SPB_17.2`，Tcl 8.6.0）里 source `probe.tcl`，得到：

```
Capture> source "C:/.../dist/probe.tcl"
[  1]missing close-brace
```

**根因不是语法，是编码。** Capture 的 Tcl **按系统代码页读文件**（中文 Windows = cp936/GBK），
而我们的 `.tcl` 是 UTF-8 + 中文注释。GBK 是双字节编码，尾字节范围 0x40–0xFE ——
**0x7B `{`、0x7D `}`、0x5C `\` 都在里面**。所以一个汉字的第二个字节被读成花括号，
括号计数就乱了，报「missing close-brace」。

量化的证据（拿当时的 probe.tcl 按 GBK 解码）：

| 项 | 值 |
|---|---|
| UTF-8 非 ASCII 字节 | 1482 |
| 按 GBK 解码后**凭空多出**的左花括号 | 109 |
| 同上，右花括号 | 102 |

**修法**：所有 `.tcl` 模板改成**纯 ASCII**（说明与界面文字改英文）。这样无论系统代码页是
GBK、UTF-8 还是别的，解析结果都一样。

新增三条回归测试（`tests/test_tcl_plugin.py`）：

1. `test_all_tcl_templates_are_pure_ascii` —— 模板里不许出现一个 >127 的字节；
2. `test_gbk_decoding_of_templates_stays_brace_balanced` —— 按 GBK 解码后花括号数必须不变；
3. 每个模板按 GBK 解码后 `info complete` 必须为 1。

> 顺带确认了两件事：第一，用户那台机器**确实是 Capture 17.2，装在一个非默认盘 `D:`**，
> 后面 deploy 要按这个路径走；第二，命令窗口**确实是 Tcl 解释器**（`info patchlevel` → 8.6.0），
> `source` 这条路本身是通的，只是文件编码把解析搞坏了。

**教训（已写进 [[feedback-windows-build-scripts]]）**：给 Cadence 用的 `.tcl`，一律纯 ASCII。
中文只出现在 Python 侧和网页界面里；要给用户看的文案在 `docs/` 或 `tk_messageBox` 里用英文。

### B11. 由探测结果暴露的一个真 bug：pcbenv 找错位置

探测输出里 `HOME : D:/Cadence/SPB_Data` —— 这是 Cadence 自己设的数据目录。
Allegro 读的是 **`$HOME/pcbenv/env`**，也就是 `D:\Cadence\SPB_Data\pcbenv\env`。

原来的 `find_pcbenv()` 只看 `HOME` / `USERPROFILE`。用户从 PowerShell 跑 `deploy` 时，
PowerShell 里通常**没有** `HOME`（那是 Cadence 启动时才设的），于是会退到
`C:\Users\32657\pcbenv` —— **Allegro 根本不看那个目录**，用户配完毫无效果。

修法：

- `find_pcbenv(cadence_root)` 按可信度列候选：`<SPB>/../SPB_Data/pcbenv`（由 SPB 根推出）→
  `$HOME/pcbenv` → `%USERPROFILE%/pcbenv` → 各盘符 `<盘>:\Cadence\SPB_Data\pcbenv`；
  优先选**已有 env 文件**的，其次选目录已存在的。
- `deploy` 从 `tclscripts` 往上退三层得到 SPB 根（`spb_root_from_tcl`），再据此推 `SPB_Data`。
- `deploy` 的路径探测也加了 `D:\Cadence\SPB_*` 这类非默认安装位置（原来只扫 `Program Files`），
  并会兜底扫描 `<盘>:\Cadence\*` 下的任何目录，防止版本号不在已知列表里。

### B15. ★ R1 解除：拿到了 Capture 17.2 的真实 OLB XML 方言

用户把参考库转换出来的 `ref.xml`（9790 字节）发了过来。**这是整个项目最重要的一个输入。**

真方言和我们之前猜的完全不同：

| | 之前猜的 | 实际 |
|---|---|---|
| 根元素 | `<CaptureLibrary Version="1.0">` | `<Lib xsi:noNamespaceSchemaLocation="olb.xsd">` |
| 元件 | `<Part Name=…>` | `<Package><Defn name=… pcbFootprint=… refdesPrefix=…/>` |
| 图形 | `<Graphics><Rectangle …/>` | `<NormalView><Rect><Defn x1 x2 y1 y2 fillStyle …/></Rect>` |
| 引脚 | `<Pins><Pin Number=… X=… Y=…/>` | `<SymbolPinScalar><Defn hotptX hotptY startX startY name position type visible/>` |
| 引脚号 | 直接写在 Pin 上 | `<PhysicalPart><PinNumber number=… position=…/>` 用 position 反查 |
| 库级设置 | 无 | `<DefaultValues>`：24 个字体 + 页面设置 + 字段映射（**PCB Footprint 是字段 8**） |

**单位**：坐标是整数，**1 单位 = 10 mil = 0.254 mm**（参考件 50×50 矩形 = 500×500 mil，
引脚长 30 单位 = 300 mil，都合常理）。

**引脚几何**：`startX/startY` 是贴本体那一端，`hotptX/hotptY` 是连接点（导线接这儿）。
我们模型里 `pin.x_mm/y_mm` 就是连接点，所以本体端 = 连接点 + 长度 × (cosθ, sinθ)。

**引脚类型编码**：参考件两个脚都是 `type="4"`，而 Capture 手放引脚默认 Passive
→ **4 = Passive**，其余按 0=Input 1=Output 2=Bidirectional 3=TriState 5=Power 推（待真机确认）。

新写 `symbol/capture_lib.py`：

- `generate_lib_xml()` 产出完整 `<Lib>`，`DefaultValues` 原样带上；
- `DefaultValues` 从 `samples/ref_capture172.xml`（用户那份）抽出，内置成
  `symbol/templates/capture172_defaults.xml`；
- `learn-schema` 现在会自动识别「真方言」并把 DefaultValues 抽成 `capture_defaults.xml`；
- `pipeline` 改成用它生成符号 XML；`olb.py` 的合并单位从 `<Part>` 改为 `<Package>`。

**结构对照验证**（生成的 RP2040 XML vs 用户的参考 XML）：

| 项 | 结果 |
|---|---|
| 元素标签种类 | 27 种 vs 27 种，**无多无缺** |
| 属性名集合 | 36 个标签逐个比对，**全部一致** |
| XML 合法性 | ElementTree 解析通过 |

新增 13 条 `test_capture_lib.py`（单位换算、方言判定、bbox/rect 为整数、引脚 start/hot 方向、
引脚号映射完整性、类型编码、refdes 去 `?`、文字默认关闭）+ 5 条 Package 合并测试
+ 1 条 pipeline 方言断言。

## D. 顶/底引脚名压字（RP2040 截图）· 2026-10-19

**现象**：57 脚 RP2040 放进 Capture 后，顶边 12 根脚（DVDD/DVDD/VREG_VOUT/VREG_IN/
IOVDD×6/USB_VDD/ADC_AVDD）的名字糊成一片；底边名字也贴着边线。

**判断**：Capture 画顶/底引脚的名字时是**横排**的。参考件里 `IsPinNamesRotated=1`
我们照抄了，但实测它并不改变单根引脚的书写方向；而 OLB XML 方言里没有任何
「让这根引脚的名字竖排」的开关（参考件结构里逐项核对过）。所以只能改几何。

**修法**（`symbol/capture_lib.py::layout_vertical_pins`）：

1. 把同一条边（同方向、同 y）上的竖排引脚按名字宽度（约 1.2 mm/字符）估算，
   相邻两列至少留 0.8 mm 空隙，必要时横向推开；整组以原中点为轴摊开。
2. 本体矩形随之加宽（左右各留 2.54 mm），BBox 自动跟随。
3. 左右两侧的水平引脚跟着自己那侧的新边线整体平移 —— 否则它们的本体端会悬空。

## E. 四周引脚排列 + 封装预览居中 · 2026-10-19（修正 D 的结论）

**调研**（按用户要求先查 GitHub 同类项目，只读事实、不拷 AGPL 代码）：
`Werni2A/OpenOrCadParser`（解析真实 .OLB 二进制）、`arthur-zyl/lcsc-library-converter`、

配合用户提供的 17.2 `olb.xsd` 与本库的 OLB2XML 回读件逐项核对，得到四条结论：

1. **D 里的「名字宽度疏排」是治标。** 真正的根因是 **`IsLong=0`**。OpenOrCadParser
   `StructSymbolPin.cpp::getPinLength` / `PinShape.hpp`：`IsLong=0` 表示「Short 引脚」，
   Capture 只画 `hotpt→start` 距离的**一半**。我们全写 0，所以 100 mil 的脚只画 50 mil，
   名字/编号的默认摆放跟着短引脚样式跑偏。→ 改为 `IsLong = 1 if 长度 ≥ 10 单位`。
   左右两边「名字框内、编号框外」是 Capture 长引脚的默认画法，IsLong 修正后自动正确。
2. **上下两边竖排名字由 `IsPinNamesRotated=1` 负责**（NormalView 级开关）。D 里说它
   「实测无效」是因为当时引脚被画成短引脚、位置全乱，误判。17.2 XSD 里虽定义了
   per-pin 的 `PinDisplayProp`，但真实导出（led.xml / led_test.xml / OpenOrCadParser 测试件）
   全都是 0 个 —— 普通引脚不写它。
3. **Y 轴必须整体翻转。** Capture 符号坐标 Y 向下，我们模型 Y 向上。两处参考实现都写

* 17.2 的 `olb.xsd` 没有 `<Text>` 元素 —— 文字图元是 `CommentText`（locX/locY/name/

## F. 引脚名自绘（CommentText + 旋转字体）· 2026-10-19（修正 E 的第 2 条）

**现象**（用户第四轮截图 + 回读件 `rp2040_v4_rt.xml`，文字：「引脚排列还是没有达到预期的效果」）：

剩下的问题只有一处：**顶/底两边的 14 个引脚名仍然是横排**，顶边 12 个名字互相叠成一片。

**为什么 `IsPinNamesRotated` 没救**（三份证据，均为只读取证）：
1. 回读件里 `<IsPinNamesRotated><Defn val="1"/></IsPinNamesRotated>` 确实是 1 ——
   开关存进去了，17.2 画图时不认；
2. 17.2 的 `olb.xsd` 里 NormalView 只有 `IsPinNumbersVisible / IsPinNamesRotated /
   IsPinNamesVisible` 三个显示开关，**没有任何 Pin Name Inside/Offset/Rotation 元素**
   （grep `inside|offset|rotate` 仅命中这两个 Rotated 定义）；
3. OpenOrCadParser `StructGeneralProperties.cpp`：引脚相关只有 3 个 bit
   （bit0 名字可见 / bit1 名字旋转 / bit2 编号可见，0xC0 必须为 0），
   `XmlExporter.cpp` 也只导出这三个开关。
   → Capture Part Properties 里的「名字在框内」是编辑器的渲染策略，OLB 二进制里
   根本没有对应字段，XML2OLB 无论怎么写都改不了。

**方案：隐藏 Capture 画的名字，改用 `CommentText` 自绘。**
* `IsPinNamesVisible=0`（只要该符号存在顶/底带名字的竖直引脚才这么做；

  `orientation=900`（LOGFONT 真字段，OLB2XML/OpenOrCadParser 都按此存取），
  即竖排 90°；
* 字体表：CommentText 在二进制里只存「字体下标」，而默认 24 个 `DefaultFont`
  全是 `escapement=0`。生成时把 `escapement=900` 的字体条目追加进

  顶 `y=边线+5+字宽`（文字向上延伸、起点靠里）；底 `y=边线-5`。

## J. 顶部取景留白（v9）· 2026-10-19

## O. 部署阶段：菜单注册修正（2026-10-19）

**现象：** 部署后 Capture 启动日志显示 `Loading .../lcsc2cadence/lcsc2cadence.tcl`
（递归扫描确实加载了主逻辑），手动 source 也打印 `menu registered`，

**根因：** `RegisterAction` 的参数不是自由字符串。Cadence 自带
`capAutoLoad\capAppLaunchMenu.tcl` 的写法：

```tcl
RegisterAction "_cdnCapTclAddPageCustomMenu"   "capTrue" "" "capAddAppLauncher" ""
RegisterAction "_cdnCapTclAddDesignCustomMenu" "capTrue" "" "capAddAppLauncher" ""
```

第 2、4 个参数是**回调 proc 名**。旧代码传 `"POPL" "Schematic"`，Tcl 把字符串当
命令名接受（不报错），但 Capture 永远不会回调 —— 所以注册“成功”而菜单不存在。
菜单条目由 builder 在 Capture 构建菜单栏时用
`AddAccessoryMenu <组名> <条目> <命令>` 添加，出现在菜单栏 **Accessories** 下。

**修正：** 注册两个 hook；builder `buildMenus` 添加三项（打开立创商城 / 能力探测 /
日志），组名「立创元件库」。中文标签用 `\uXXXX` 转义，模板保持纯 ASCII
（Capture 按 cp936 读文件，UTF-8 中文字节会破坏 Tcl 解析）。注册失败时由轮询循环
每 2 秒重试（前两分钟）。tclsh 下用桩 `RegisterAction/AddAccessoryMenu` 验证过

覆盖到 `capAutoLoad\` 与 `capAutoLoad\lcsc2cadence\` 后重启 Capture。

## P. B4 放置失败：ORCAP-1687 根因与修复（2026-10-19）

**现象：** 商城双击 RP2040 后 Capture 弹
`ERROR(ORCAP-1687): Macro Player. Unable to place object.`，符号未落图。

**根因：** 库里的零件名与 `PlacePart` 传的名字不一致。

- `stage_component` 生成符号 XML 时把 **Package 名设成了封装名**
  （如 `LQFN-56_L7.0-W7.0-P0.4-EP`：`generate_lib_xml(package_name=fp_name)`）；
- 放置请求却传 **符号名** `RP2040`（server / CLI 三处都是 `comp.symbol.name`）；
- Capture 在库里找不到叫 `RP2040` 的零件 → Macro Player 报 1687。

早期验证（v8–v11）之所以没暴露：那几轮都是把 OLB 导入后**在库窗口里手动双击**
打开零件编辑器，而不是走 PlacePart；且零件编辑器按 PartValue 显示 `RP2040`，
所以肉眼看起来名字没错。

**修复：**

1. `pipeline.stage_component` / `cmd_build`：Package 名统一取 **符号名**
   （无符号名才退回封装名）；封装名仍写进 `pcbFootprint` 属性。
2. TCL `buildOlb` 增加**合并后核对**：在 merged XML 里查 `<Package ... name="<partName>">`，
   查不到就直接报 `part 'X' not found in merged library XML (first package: 'Y')`
   —— 以后同类问题在放置前就能看到明确原因，而不是一句 1687。
3. `placePart` 记录完整调用（坐标 / 库 / 零件名）到日志。

## Q. ORCAP-1687 第二轮：不是名字问题，是「库缓存 + 文件锁」（2026-10-19，已修）

P 段的修复（Package 名 = 符号名）是对的，真机重试仍然是 1687。三轮诊断脚本
（`outputs/lcsc2_place_diag.tcl` v2–v5）在用户机上取得的证据：

1. **PlacePart 签名正确**：`catch {PlacePart}` 报
   `Wrong number of arguments :PlacePart x y libName pkgName device boolvalue6`；
   用自带 `discrete.olb` 放 `R` 一次成功 → 调用方式/坐标/上下文都没问题。
2. **合并产物正确**：`C2040.merged.xml` 的包名是
   `{LQFN-56_L7.0-W7.0-P0.4-EP RP2040}`，根 `<Defn>` 指向 project.olb。
   但回读 project.olb 只有 `LQFN-56_...`。
3. **`XMATIC_XML2OLB` 对已存在的 .olb 静默不写**：目标文件存在时它照样回
   `_xxxx_p_DboState`，mtime/大小纹丝不动。同一份 merged XML 写成**新路径**
   （probe.olb / project_new.olb）立即成功，回读两个包齐全。
4. **`file rename` 能绕过锁**：把 project.olb 改名挪走后，写同名新文件成功，
   回读含 RP2040。
5. **但 PlacePart 仍报 "Invalid Path or Invalid Argument(s)"** —— PlacePart
   **按路径缓存库内容**，磁盘上的文件换了也不重读。
6. 对照：`project_new.olb`（新路径）`PlacePart ... RP2040` 一次成功，零件真的
   落在了原理图上。→ 结论：只要给 PlacePart 一个本会话没见过的新路径即可。

**修复（TCL 模板）：**

- 新增 `writeOlb`：目标已存在时先 `file rename -force` 挪到 `.old` 再写
  （删不掉/覆盖不了的已加载库可以改名），写失败时恢复原文件。
- 新增 `olbHasPart`：XML2OLB 之后用 OLB2XML **回读核对**零件名在不在 ——
  不相信 DboState 返回值，只相信文件内容。
- `buildOlb` 分两步产出：① 工程库 `project.olb` 照旧**累加**（best effort，
  写不进去只记 WARN）；② 每次放置另写一份
  `staging/<Cid>/place_<毫秒>.olb`，**新路径**，PlacePart 指向它 → 不会命中
  旧缓存。旧副本只保留最近 5 份（`prunePlaceCopies`）。
- 回归测试：OLB2XML 桩改为"回读 .olb 里记录的生成源"，使 `olbHasPart` 真正被
  执行到；新增断言「PlacePart 的库参数必须是本次新建的 place_*.olb」。
  **177 passed。**

**经验（以后别再踩）：**

- `XMATIC_XML2OLB` / `XMATIC_OLB2XML` 的返回值不可信，一切以文件为准；
- 对 Capture 已经加载过的 .olb：**覆盖 = 静默失败，改名 = 成功**；
- PlacePart 的库内容按**路径**缓存，改写同一路径对它无效，换新路径立即可用。

## T. 双击后自动切到 OrCAD（2026-10-19）

- `_place` 收到请求时 `GetForegroundWindow()` 记下浏览器窗口；

  （exe 位于 SPB 目录且名为 capture/orcap，或标题含 "OrCAD Capture"），
  `IsIconic` 则 `SW_RESTORE`，随后 `SetForegroundWindow`（失败时用
  AttachThreadInput 绕过前台锁）；
- 非 Windows 全部空操作；配置 `switch_to_capture`（默认 true，商城设置可关）。

## U. 内嵌到 Capture 页签（学习 iDesign，2026-10-19）

用户在 B 站看到同类商业插件 iDesign Capture：商城嵌在 OrCAD 主窗口里，观感与原
生界面一致。实测 Capture 17.2 自带嵌入浏览器：

- `OpenURL <url> <label>` → 在 Capture 中打开一个 **HTML 页签**（与 MarketPlace /
  Start Page 同一机制），本地 `http://127.0.0.1:...` 可正常打开，签名是
  `OpenURL url pTitle`（3 参报 wrong # args）；
- 内嵌内核是 **MSIE 7.0 / documentMode 7**（Trident 7 的 IE7 兼容模式）：
  无 fetch / Promise / JSON / querySelectorAll / addEventListener / SVG / canvas / flex；
  有 XHR 与 ActiveXObject。**现有现代前端在页签里完全不执行。**

因此新增**内嵌专用前端**（`server/web/embed.html` + `embed.js`）：

- ES3 写法（var / function / attachEvent 兼容分支 / 无模板串），表格布局，无 CSS 变量；
- 数据全部走 **JSONP**（脚本标签 + 回调），服务端在 `?cb=` 存在时返回
  `/*lcsc*/cb(...);`：`/api/es/search|browse|categories|part|status|place`；
- 放置用 `/api/es/place?cid=`，服务端识别为内嵌来源，**不切窗口、不最小化**；
- 双击列表行即放置，提示"在 Place Part 面板里双击零件、点画布落位"；
- SVG 预览在内核不支持时自动隐藏并提示改用"打开商城（浏览器）"。

服务端：`serve_forever` 启动时把实际 URL 写入 `%LOCALAPPDATA%\lcsc2cadence\url.txt`；
TCL `ensureServer` 读它并探测端口（socket），失效则 `exe serve &` 重新拉起并轮询。
菜单新增两项：「打开立创商城」（内嵌页签，`OpenURL <url>/embed`）与
「打开商城（浏览器）」（旧的外部窗口方式）。缺 `OpenURL` 的版本自动退回外部方式。

测试：`test_server.py` 新增 embed 页面 / JSONP / ES3 语法 / 内嵌放置不切窗口
（186 passed）。

## V. 面板 vs 直接放置的最终判定（2026-10-20）

在**全新工程 + 清空页 + v12 符号 + 明确选中 `LCSC_TEST`（lib=2 part=0）** 条件下
再次测试 Place Part 面板流程：

- 跟随光标：**正常**（面板会自动武装点击放置）；
- 但落位后的符号**引脚仍然散落在框外** —— 与旧库、旧工程、旧符号都无关。

对照事实：**同一个 `.olb`（含规范化后的副本）直接 `PlacePart` 放置完全正确**
（多次、多版本一致）。结论：Capture 17.2 的 Place Part 面板在实例化「自绘
CommentText 符号」时存在兼容缺陷，无法通过数据侧修复。

**最终方案：**

1. 放置一律走直接 `PlacePart`（英寸坐标、4×3 英寸格点、`ZoomRedraw`+`ZoomAll`），
   不使用面板、不跟随光标（代码保留 `placeInteractive/armClickPlace`，供未来版本
   验证或用户手动调用）；
2. 面板路径不再作为默认；`follow_cursor` 请求在插件内被强制为固定位置；
3. 引脚编号重复问题由 **v12 生成器**解决：`IsPinNumbersVisible=0` 全局关闭 +
   四边全部自绘编号（57 个 CommentText）。换库后需重启 Capture（路径缓存）。

**已知限制（写入 README）：** 双击后在下一个格点落位，需要手动拖到位；这是
Capture 面板缺陷所致，不是实现取舍。
