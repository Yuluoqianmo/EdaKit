## 当前界面问题

基于用户约808px停靠截图与当前layout代码：大标题、搜索和固定筛选区使结果起点约在顶部280px后；右侧固定300px详情进一步压缩列表，型号、厂商、库存被截断。详情的文本区与预览区用固定高度分割，未随内容变化分配空间。普通操作的等待反馈刚刚完成安静化，应保留此方向。

## 推荐布局：停靠优先的器件工作台

浅色、低装饰密集工具界面。字号13px正文、11–12px辅助，主标题16px，控件约30–32px高。主色保留低饱和青绿色，深色只用于文字和少量标题。减少卡片嵌套、投影和品牌横幅，不添加全局动画。

- 700–950px主目标：顶部紧凑搜索与条件，中央全宽结果表，下方选中器件检查区（左资料/操作，右预览）。避免把结果表压缩成窄栏。分隔条可调上下比例，设置最小列表/预览高度。
- 约1050px以上：结果在左、详情在右，可调整比例。分类/参数按需展开，默认不长期占用左侧宽度。
- 小于640px：结果与详情可切换，保留返回列表与当前选择；不把多列桌面布局硬压进窄面板。具体断点以原型和Capture验证确定。
- 顶部控制区目标约130–160px：小标题/连接状态、搜索行、分类面包屑与常用筛选、已应用条件。全部参数在独立可搜索面板中，保留多选与应用查询。
- 表格优先显示完整型号/C编号、厂商、封装、库存、价格。型号列优先分配宽度，说明进入详情；允许用户显隐部分列，固定表头和分页。
- 选中后立即使用已有行数据展示概要；CAD、资料、当前预览分别加载，失败互不拖垮。放置按钮位置稳定，是否可放置以符号可用状态为准。
- 保留当前草稿/已查询条件区别。选择分类或修改筛选不偷偷刷新商品，Enter/查询显式提交；删除条件同样遵循这一语义。
- 保留先准备再原生光标放置，焦点仅在用户放置动作中切换，查询/预览不得抢原理图焦点。正常反馈局部展示，取消/失败/重试仍可见。

概念图仅作为讨论样稿，表中库存/价格/型号组合为示例；不是联网结果或最终像素规范。批准布局后再补齐空态、加载、错误、参数展开及宽窄状态。

## CEF技术约束

本机已测Chrome45，JSON/XHR/Canvas2D/Flex/requestAnimationFrame可用，WebGL1/2未取得上下文。新界面用兼容JavaScript、Flex/普通表格和PNG即可实现；不依赖CSS Grid、CSS变量、ES modules、async/await或现代浏览器专属组件。React/Vite并非本轮默认迁移方向，框架替换不能当作性能优化依据。

建议CEF优先XHR+JSON，保留旧入口JSONP兼容层。XHR允许前端取消连接，但不等于终止已经开始的后端计算；后端需要独立的调度/过时任务处理。此项可分阶段引入，避免同时重写整个业务。

## 源码审计：已确认事实与优化候选

| 事实 | 候选修改 | 验证重点 |
|---|---|---|
| server/app.py 的_send对所有响应发Cache-Control:no-store | 静态资产按构建版本缓存；PNG按元件数据版本、类型、尺寸、角度缓存。商品价格库存仍需时效策略 | 切回已看过预览的请求/渲染次数；升级后资源不陈旧 |
| embed.js小预览最低也请求1024；后端允许512 | 普通预览按容器及DPI选择512，放大时再提升；3D继续按后端上限处理 | 清晰度、生成耗时、内存；像素数减少不等于耗时同比减少 |
| 3D已有OBJ缓存8、parse_obj缓存8、render_model_png缓存12 | 保留并优化既有缓存；明确字节预算和失效版本，同key并发合并，避免重复未命中工作 | 冷/热缓存与并发场景分开计时，不重复宣称首次下载 |
| 不同角度会生成新PNG；目前松开鼠标后才请求，非每帧请求 | 先保留旧图、按最终视角渲染；低分辨率优先，是否补高清由测量决定；限制并发、只优先最新选择 | 快速连续拖动不积压CPU，最终画面与角度一致 |
| _do_place调用stage_component默认download_step=True，并生成封装相关产物 | 新增Capture专用准备路径，符号所需数据优先；STEP/Allegro产物通过独立导出保留，不能悄悄删除原能力 | 分段记录准备、排队、库合并、PlaceNew耗时，回归库属性/引脚/既有产物约定 |
| Python CPU逐像素3D渲染；ThreadingHTTPServer不代表CPU渲染可以无限并行 | 有界渲染调度，缓存命中优先；必要时评估独立进程/原生加速，暂不预选新依赖 | 多次拖动/选中时查询和放置不被大量渲染拖慢 |
| layout混合读取尺寸与写入样式，resize可触发renderPreview | 合并resize到一次requestAnimationFrame，先读后写；尺寸跨档再请求新PNG | 拖动面板宽度时布局次数、图片请求和滚动流畅度 |
| CAD缓存字典未见容量上限，商品详情缓存有128项/600s策略 | 分类/商品/CAD/模型缓存拆分管理，有界容量和数据版本；库存价格不能长期固定 | 长期使用内存上限、过期刷新、无串料 |

以上为代码路径发现，不是测得的瓶颈占比，不承诺倍数提升。首选项为Capture放置准备拆分、预览尺寸与缓存、渲染调度；布局与请求层随后按实际收益推进。无需为50条分页表格先引入复杂虚拟列表。

## 实施顺序与验收

1. 确认停靠主布局与图示方向，做隔离可交互原型；覆盖808×850、700×850和宽屏，验证型号可读、筛选可达、放置按钮固定。
2. 建立轻量分段计时，样本覆盖电阻与复杂IC、冷/热缓存、首次/重复放置。记录请求数、下载/解析/渲染/显示、队列与库合并耗时；只在日志保留诊断，不增加用户进度弹层。
3. 先做后端关键路径与预览缓存/分辨率，单独回归；再接新UI和XHR兼容层，避免一次混入全部变化。
4. 用同一组样本比较变更前后，给出中位数/尾延迟、缓存命中与内存。外部商城响应波动与本地处理分开报告。
5. 每一阶段保留旧UI和可回退包。Capture真机验收中文输入、焦点、查询/参数、预览、放置/引脚/Esc和多DPI；确认后再成为默认入口。

本轮结论：采用原生工具式UI，按面板宽度调整信息结构；性能从减少关键路径工作和无效请求入手。当前正式版本继续使用，不在方案讨论时替换。
