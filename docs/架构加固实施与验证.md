# 架构加固实施与验证

日期：2026-10-21。范围来自《架构评估与扩展建议》。本轮落地现有应用的扩展边界与可靠性措施，不新增第二数据源、新宿主或批量业务功能。

## 实施内容

| 边界 | 已落地实现 |
| --- | --- |
| 应用服务 | services 下新增 CatalogService、ComponentService、PreviewService、PlacementService、ExportService；HTTP 负责解析和响应，CLI 放置共用 PlacementService，独立 build 与日常 staging 共用转换流水线 |
| 依赖契约 | CatalogProvider、ComponentProvider、ModelProvider 结构化契约，服务可注入数据源工厂、缓存、模型加载器和转换函数；make_server 支持注入服务集合 |
| 配置 | config.py 独立管理配置；旧入口兼容导出 Config/app_dir；无版本旧配置按 v1 读取，验证类型、模式、端口、有限坐标；未知字段保存在 extra，已有绝对库路径保留；无效或更新版本的当前配置明确拒绝，不用默认值覆盖 |
| 文件发布 | 请求、响应、配置及服务 URL 完整写临时文件后原子发布；Python 与 Tcl 针对 Windows 短暂的共享冲突进行有界重试 |
| 队列协议 | v2 新增 command、target_session、expires；新 Tcl 继续接受 v1；请求 ID 有格式限制和提交收据，同 ID 重试不再次执行；默认有效期 300 秒 |
| 宿主路由 | Tcl 每次进程启动生成会话标识，并加入工作台 URL；前端 API 自动携带会话；提交前后确认目标仍存活，多实例且未指定目标时拒绝歧义操作；在线状态按绑定会话判断 |
| 独占消费 | Tcl 通过不覆盖的原子改名领取 .req 为 .req.PID.work；其他消费者无法领取同一请求；已有响应的请求不重放 |
| 共享 OLB | 跨 Capture 的累积库生成/合并阶段使用文件锁串行化；锁内容先写好，再通过本地硬链接原子取得锁；服务只在验证进程已退出或 PID 已复用后清理遗留锁 |
| 失败恢复 | 服务每秒巡检队列；过期请求失败返回；宿主退出时已领取任务标记 interrupted，等待原理图的中间状态更新为失败；未领取但目标已关闭的请求拒绝执行；不自动重放有副作用的请求 |
| 前端 | frontend 下拆为核心、反馈、条件、API、目录、选择、预览、布局、放置、事件模块；状态按功能所有者分组；构建时组合成单闭包 ES3 文件，维持一次 JS 加载；CSS 分基础和工作台两个有序层，保留已验证的级联 |
| 构建约束 | tools/build_web.py 生成资源，--check 检查同步；测试及 PyInstaller spec 拒绝过期资源，避免改了源码但发出旧页面 |
| 缓存 | 独立的组件、商品、分类、封装与参数缓存，容量/TTL 受控，线程同步，相同键正在加载时共用结果；生产缓存归服务实例所有，不再混在 app.py 全局字典里 |
| 任务与连接 | HTTP 工作连接上限 48，读取超时 30 秒；预览并发 4、等待队列 16、排队超时 25 秒；按页面/图像通道和递增版本丢弃排队中的旧预览，保留原有 CPU 渲染单槽与结果缓存 |
| 可观测性 | HTTP 错误携带 requestId/errorCode；放置用 seq 关联 Python 与 Tcl 日志；service.log 按 2MB、3 个备份滚动；edakit.log 保留宿主诊断，background.log 保留异常输出 |

## 兼容与实际语义

CEF 的 HTML 布局、静态等待提示和原生 PlaceNew 链路保留。前端仍支持 XHR/JSON 和 legacy JSONP，模型仍由服务端 PNG 路径预览，不依赖 WebGL。Tcl 模板保持纯 ASCII。

浏览器入口继续使用 Capture 专用准备；POST 完整准备、CLI stage/build 的导出语义保留。独立 bundle 不采用或修改用户安装库目录，独立运行脚本、完整器件名称和内部安全别名保持一致。CLI stage-only 仍允许仅有封装的数据。

新 Tcl 可读取旧协议。升级时必须重新启动全部 Capture，以避免旧 Tcl 与新生产者混用。会话跟踪不再依赖 30 秒心跳判断宿主死亡，但没有绑定会话的旧状态 API 仍保留心跳兼容行为。

“place/armed”表示宿主已启动交互式放置，不表示用户已经点击完成落点。“interrupted”表示宿主在过程内退出，可能已产生部分结果，必须查看原理图后决定重试。

不能中途打断已经执行中的原生 Capture 操作或纯 CPU 渲染。任务替代只保证排队阶段的旧工作被丢弃；正在执行的工作通过并发上限约束。缓存与提交收据保留不等于建立了用户可见的任务历史数据库；收据和响应暂保留用于排障，不自动删除历史记录。

Provider 契约为当前适配器提供替换边界，当前公开接口仍使用 LCSC CID。第二数据源实际接入时还需定义带来源的器件标识与字段映射；没有宣称任意供应商已可直接接入。Allegro 深度原生集成仍不在本轮范围。

- 真实 Tcl 子进程同时竞争同一请求，确认只执行一次，另一会话不领取该请求。仍是宿主桩测试，不替代原生 Capture 多实例操作。
- 导出验证：超长器件名生成的 XML 与放置 Tcl 使用同一安全别名；封装产物正常；有符号与无符号 stage-only 路径均覆盖。

性能证据以资源与重复工作的控制为主：缓存并发测试中 10 个同键请求只触发 1 次加载；任务和连接上限由测试验证。未把这些结果换算为真实商城查询速度提升比例，也没有进行长时间现场内存压力测试。

## 交付、回退与真机补验

主安装入口为 `E:\outputs\edakit\dist\edakit.exe`，诊断入口为同目录 edakit-cli.exe。构建暂存位于 dist/architecture-hardening；SHA256.json 记录交付散列。部署后主程序、CLI、Tcl 必须保持同一版本。

回退备份：dist/rollback-before-architecture 下保存更新前的两个 exe、Tcl 模板和当前安装副本；源码改动前的 ZIP 位于 E:\outputs\backups，文件名以 edakit-before-architecture 开头。需要回退时先退出全部 Capture，恢复两个 exe，再用恢复后的 CLI deploy，使安装 Tcl 同步；不删除配置、旧库路径或历史队列数据。

本轮真实 Capture 尚待以下补验：

1. 重新打开 Capture，进入 EdaKit → LCSC Mall，查询、预览并放置普通器件和 C5123614，点击落位后 Esc 退出。
2. 同时打开两个 Capture，从各自工作台发起放置，确认只在对应原理图出现；关闭一个后另一个正常使用。
3. 准备好器件但未切回原理图时关闭对应 Capture，确认该任务不会在其他 Capture 自动执行。
4. 关闭最后一个 Capture，观察 edakit.exe 的冻结启动器和工作进程均退出；再打开时工作台正常恢复。

此前用户已确认上一版功能和生命周期测试正常；这不代替本轮协议与锁变更后的真机验收。
